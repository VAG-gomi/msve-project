# MSVE-WO-1.9G Correction Report — Candidate 0.8.9.7

**Work order:** MSVE-WO-1.9G (Query Identity and Invocation Encoding Conformance)
**Base:** Candidate 0.8.9.6
**Date:** 2026-10-12
**Status:** CORRECTION CANDIDATE — NOT APPROVED, NOT FROZEN, NOT RELEASED

## Summary

Candidate 0.8.9.7 corrects three P1 source-level mismatches and three P2
issues from the owner's review of 0.8.9.6. All changes are within the approved
design. No new architecture.

## P1 findings corrected

### 1. Verification-input fallback hash

**Finding:** Spec defined fallback as `SHA256(canonical_query_bytes)`. Implementation
computed `SHA256(qid.encode("utf-8"))` — hashing the hex digest text, not the query bytes.

**Correction:** The pipeline now uses `qid` directly as the fallback. The `query_id`
function already computes SHA-256 over canonical query bytes, so `qid` IS the
correct fallback. No double-hashing.

**Test:** `test_97_verif_inputs_is_qid` independently computes the expected SHA-256
from canonical bytes, asserts exact equality with `verification_inputs_ref`, and
asserts inequality with the double-hashed (wrong) value. This test fails under
the old behavior.

### 2. Invocation-ID encoding alignment

**Finding:** Normative: `enc_str(s) = u32be(len) || UTF8(s)`. Implementation prepended
`0x01` to every string, producing different IDs than the published algorithm.

**Correction:** The prototype's `_invocation_id()` now uses the exact normative
encoding for required fields (no `0x01` prefix). The optional-value `0x00`/`0x01`
encoding is reserved for descriptor fields, not invocation IDs. All invocation
fields are required; `None` is rejected by assertion.

**Test vectors:** `INVOCATION_VECTORS.md` publishes a deterministic vector with
the complete field values and expected invocation ID
(`f082b983...fc0b`). `test_97_invocation_id_matches_vector` asserts the
implementation reproduces it exactly. The vector was generated by an independent
reference implementation.

### 3. Solver configuration provenance (Option A)

**Finding:** `solver.run()` accepted `config` but never applied it to Z3. The
recorded config overstated what was actually configured.

**Correction (Option A):** Only the `"default"` profile is supported. The solver
rejects any other profile value with `INVALID_INPUT`. The `"default"` profile
applies no custom Z3 settings beyond the timeout. The recorded config therefore
truthfully describes the applied configuration.

**Test:** `test_97_unsupported_config_rejected` verifies rejection of
`"aggressive"` and acceptance of `"default"`.

## P2 corrections

### 4. CAPACITY_EXCEEDED in §E.3

Added `CAPACITY_EXCEEDED` to the §E.3 inconclusive reason-code list, matching
the closed `ReasonCode` type. Test `test_97_capacity_exceeded_consistent`
verifies the pipeline uses the enum value.

### 5. M8 provenance reconciliation

The spec's "Machine-checked" paragraph now explicitly states the 6/6 result was
verified 2026-10-12 on candidate 0.8.9.4 and is inherited as evidence for
0.8.9.5–0.8.9.7 (grammar/examples unchanged). This reconciles the spec statement
with the correction reports.

### 6. Manifest commit identities

Manifest commit SHAs are now taken directly from `git rev-parse HEAD` (40-char).
All references verified to resolve.
